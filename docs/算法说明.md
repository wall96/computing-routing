# 算法说明

本仿真器为每个业务做两件事：选择在哪颗卫星或地面节点上计算，以及规划数据怎么走。数据先从源送到算力节点（前段），计算、压缩后再送到各目的（后段）。

共有 8 种求解器：

- **S0～S5**：每个业务只选 1 个算力节点，不拆分。
- **S6、S7**：可以把一个业务包拆成多个子包，分到多个算力节点并行计算。

所有求解器都调用 [solvers/base.py](../solvers/base.py) 中同一套约束校验和时延、能耗计算，保证对比口径一致。

## 1. 公共模型

### 1.1 网络

- 每 30 s 生成一个网络快照。快照包含卫星位置、星间链路、星地链路，以及链路的时变速率。
- 地面终端只与仰角不低于门限的卫星建立星地链路。
- 终端只能作为路径的起点或终点，不参与计算，也不能被用来中转其它业务的数据。

### 1.2 时延（包模型）

一个业务数据包大小为 D（bit），计算量为每 bit ω 次，压缩比为 ρ。

| 分量 | 计算方式 |
|---|---|
| 传播时延 | 路径上各链路传播时延之和 |
| 传输时延 | D ÷ 路径上最慢一跳的速率（直通转发）。后段数据量为 D×ρ |
| 计算时延 | 固定开销 + D × ω ÷ 节点算力 × 1/(1 − 节点利用率) |

后一项 1/(1 − 节点利用率) 是算力的排队放大：节点越忙，计算越慢。

不拆分时：

> 总时延 = 前段传播 + 前段传输 + 计算 + 后段传播 + 后段传输

### 1.3 硬约束

| 约束 | 要求 |
|---|---|
| 时延 | 到每个目的的时延都不超过业务时延预算 |
| 丢包 | 端到端累计丢包率不超过业务丢包预算 |
| 带宽 | 前段每条链路要预留速率 r₀，后段每条链路要预留 r₀×ρ，都不能超过链路剩余带宽 |
| 算力 | 节点剩余算力不少于 r₀×ω |
| 功率 | 节点剩余功率不少于 η × r₀ × ω（η 为每次运算能耗） |

### 1.4 三种优化策略

S0～S5 支持以下三种策略，S6、S7 目前只支持 latency。

| 策略 | 链路权重 | 节点代价 |
|---|---|---|
| latency | 链路传播时延 | 计算时延 |
| balance | 加入本业务后链路利用率的增量 | 加入本业务后节点利用率的增量 |
| energy | 链路每 bit 能耗 × 比特数 | 计算能耗 |

## 2. 单节点算法（S0～S5）

| 算法 | 文件 | 思路 | 适用场景 |
|---|---|---|---|
| S0 最近节点 | [s0_nearest.py](../solvers/s0_nearest.py) | 从源做 BFS，按跳数由近到远逐个尝试算力节点，取第一个满足全部约束的。不看时延和能耗 | 朴素基线，作为对比的下限 |
| S1 加权 Dijkstra | [s1_dijkstra.py](../solvers/s1_dijkstra.py) | 按所选策略的链路权重，从源和各目的分别做一次 Dijkstra。对每个候选节点，得分 = 前段代价 + 后段代价 + 节点代价，按得分从低到高校验。energy 和 balance 策略下若全部失败，再按 latency 排序补试一轮 | 主力启发式，速度快 |
| S2 K 最短路 | [s2_ksp.py](../solvers/s2_ksp.py) | 先用 S1 排序。若前 M 个候选的最短路径违反约束，对这些候选用 Yen 算法找 K 条备选路径来补救 | 约束较紧、单条最短路常不满足时 |
| S3 LARAC | [s3_larac.py](../solvers/s3_larac.py) | 拉格朗日松弛：边权 = 代价 + λ×时延，迭代调整 λ，在满足时延预算的前提下使能耗或均衡代价最小 | energy、balance 策略下的时延约束最短路。latency 策略下等价于 S1 |
| S4 蚁群 | [s4_aco.py](../solvers/s4_aco.py) | 以 S1 的解作为初始最优解，在前 M 个候选节点 × K 条备选路径中，用信息素引导搜索更优组合 | 全局搜索，结果不劣于 S1，但较慢 |
| S5 MILP | [s5_milp.py](../solvers/s5_milp.py) | 对单个业务，用混合整数规划精确求解节点选择和两段路由（需要 pulp） | 小规模最优参照。图超过 80 个节点时直接跳过，无法用于全量星座 |

S1～S5 在包模型下的限制：
- 路径搜索的边权只考虑传播时延，没有计入传输时延。
- 最终校验会计入传输时延，所以结果仍然满足约束，但选出的节点不一定是时延最优的。
- 实验中用"最优单节点"作为不拆分的基线。它是 S6 设 `max_splits=1`，候选生成和时延计算与 S6、S7 完全相同。

## 3. 星上拆分算法（S6、S7）

### 3.1 拆分规则

1. 终端没有算力，不能拆分。数据包必须整包上行到一颗接入卫星，在该卫星上拆分。
2. 拆分有开销，与包大小成正比，默认每 Tbit 0.01 s。
3. 子包经星间链路送到不同的算力节点，各自计算一部分数据，再分别送往目的终端，在终端汇合。
4. 整包时延取最晚到达的子包。只有拆分后比不拆分更快才拆，否则退回最优单节点。

### 3.2 子包到达时间

接入卫星为 A，子包 k 分到比例 xₖ，在节点 vₖ 上计算：

> tₖ = 上行传播 + 整包上行传输 + 拆分开销 + 星间传播ₖ + 固定处理 + 后段传播ₖ　（固定部分 dₖ）
> 　　+ xₖ × (整包星间传输ₖ + 整包计算时延ₖ + 整包后段传输ₖ)　（比例部分 aₖ × xₖ）

即 tₖ = dₖ + aₖ × xₖ。多目的业务的后段取到各目的中最慢的那一条。

### 3.3 候选生成

- **拆分点**：取上行最快的 3 颗覆盖卫星作为候选拆分点（`max_access`）。上行时间 = 传播 + 整包传输。
- **算力节点**：对每个拆分点 A，从 A 出发做 Dijkstra（边权 = 传播 + 比特数 ÷ 速率），从各目的反向做 Dijkstra。选综合距离最近的 40 个算力节点作为候选，每个候选算出 dₖ、aₖ，以及算力、功率、带宽所允许的最大比例 capₖ。

### 3.4 S6 等完成时间注水法

[s6_waterfill.py](../solvers/s6_waterfill.py)

目标是让最晚到达的子包尽量早到。最优解有一个性质：所有分到数据的子包同时到达，设这个时刻为 τ。于是：

> xₖ = clip((τ − dₖ) ÷ aₖ, 0, capₖ)，并且 Σ xₖ = 1

求解过程：
1. 把所有候选的 dₖ 和 dₖ + aₖ×capₖ 作为断点排序。Σxₖ 是关于 τ 的分段线性递增函数，在断点间线性插值，找到 Σxₖ = 1 的 τ。
2. dₖ ≥ τ 的候选分不到数据。所以用几颗星、拆成几份，由算法自己决定。

为保证子包之间互不影响（注水法的前提），A 的每条出发星间链路只保留 dₖ 最小的一个候选。A 只有 4 条星间链路，加上 A 自身，所以 S6 最多拆成 5 份。

解出后用精确模型核算一次（包括子包共用下行链路的情况）。若不满足约束，去掉 dₖ 最大的子包重解。最后与最优单节点比较，取更快的方案。

复杂度：每个拆分点只需一次排序和一次扫描，O(n log n)。

### 3.5 S7 按 τ 分段线性规划

[s7_split_lp.py](../solvers/s7_split_lp.py)

目标与 S6 相同，但显式考虑同一业务的多个子包共用链路的情况。共用链路上，各子包的比特数相加后按该链路速率串行发送，与精确模型的口径一致。因此 S7 允许多个子包走同一条星间链路，可以拆得更细。

对每个拆分点 A，候选按 dₖ 从小到大排序。第 m 段只允许前 m 个候选参与，求解下面的线性规划：

```
min  τ
s.t. Σ xₖ = 1,  0 ≤ xₖ ≤ capₖ
     uₖ  ≥ Σᵢ xᵢ·比特数ᵢ(e) ÷ 速率(e)    对 A→vₖ 段上的每条链路 e
     wₖⱼ ≥ Σᵢ xᵢ·比特数ᵢ(e) ÷ 速率(e)    对 vₖ→目的 j 段上的每条链路 e
     固定部分ₖⱼ + 计算时延ₖ·xₖ + uₖ + wₖⱼ ≤ τ
     Σᵢ xᵢ·带宽需求ᵢ(e) ≤ 剩余带宽(e)    对每条链路 e
```

uₖ、wₖⱼ 分别是子包 k 在星间段、到目的 j 的后段上的传输时延上界。

逐段增大 m。当最优 τ ≤ d₍ₘ₊₁₎ 时，后面的候选不可能再改善结果，停止。

线性规划的最优解常常不唯一，例如几个共用上行链路的候选之间可以任意分配比例而 τ 不变。为避免多余的子包，求出解后逐个去掉比例最小的子包重解，只要 τ 不变差就接受。

线性规划没有建模丢包，由最后的精确校验兜底。求解器使用 scipy 的 HiGHS。

### 3.6 S6 与 S7 对比

| | S6 注水法 | S7 分段线性规划 |
|---|---|---|
| 共用链路 | 不允许，每条星间链路只放一个子包 | 显式建模，允许共用 |
| 最多子包数 | 5 份（4 条星间链路 + 接入卫星自身） | 不限，实验中最多 9 份 |
| 求解方式 | 闭式解 | 每个拆分点解若干次线性规划 |
| 求解耗时（HC 实验） | 8 ms | 19 ms |
| 时延（HC 实验，比最优单节点） | 快 13.3% | 快 16.9% |

## 4. 主要配置项

| 配置项 | 含义 | 默认值 |
|---|---|---|
| `simulation.solver` | 求解器 S0～S7 | S1 |
| `simulation.strategy` | latency / balance / energy | latency |
| `algorithm.split.max_splits` | 子包数上限。0 表示不限，1 表示不拆分 | 0 |
| `algorithm.split.overhead_s_per_Tbit` | 拆分开销 | 0.01 |
| `algorithm.split.min_gain_ms` | 拆分至少要比不拆分快多少才拆 | 0 |
| `algorithm.split.max_access` | 候选拆分点个数 | 3 |
| `algorithm.split.lp_max_candidates` | S7 每个拆分点参与线性规划的候选数上限 | 12 |
| `algorithm.split.lp_per_uplink` | S7 每条星间链路方向最多保留的候选数 | 2 |
| `traffic.qos.<业务>.packet_bits` | 包大小范围（bit）。删除该项则回到旧的流式模型 | — |

## 5. 已知局限

- **链路排队**：没有建模。传输时延按链路物理速率计算，不随其它业务的占用变化。只有算力的排队放大。
- **策略支持**：S6、S7 只支持 latency 策略。
- **同片内顺序**：同一时间片内业务按顺序分配，后分配的业务不会回头更新先分配业务的时延，先分配的业务时延偏乐观。
- **S5 规模**：图超过 80 个节点时 S5 跳过，不能用于全量星座。
